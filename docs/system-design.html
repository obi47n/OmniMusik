System design · OmniMusik

OmniMusik System Design

How the pieces fit: an iOS client that unifies three music sources it does not equally control, a sync API, a web control plane, and the AWS that runs them. Each section is a diagram, then what the diagram cannot show — the reason it is shaped that way.

1 · System context

Who talks to whom. Solid lines carry data OmniMusik owns; dashed lines are commands sent to audio OmniMusik never touches.

The client is the product; the server is a convenience for it. Owned files never leave the phone — uploading them was rejected as a feature, since it turns a music tool into a file host with a storage bill and licensing questions. The API holds playlists: ordered lists of references to tracks, plus enough of a snapshot to display them without asking anyone.

The constraint everything answers to

Apple Music audio is DRM-protected and decoded by a system player; Spotify audio is decoded by the Spotify app. Neither hands out samples. Effects therefore exist for owned files only, and the domain model says so — TrackSource.supportsAudioEffects is false for both streaming sources — rather than leaving it as a comment somebody will one day read as a to-do.

2 · The two protocols

The centre of the design. Two questions that look like one question and are not.

The obvious design is one Service type that browses and plays. It is wrong because the two capabilities do not line up:

  • A lapsed Apple Music subscription still lets you browse the catalogue but not play it — browsable, not playable.
  • A provider can play a track its source no longer lists — a playlist entry whose catalogue entry has been withdrawn.
  • Spotify can be connected for browsing (a web token) while playback is unavailable (the app is not installed, or is suspended).

Merged, one interface would have to lie about at least one of those states. Separate, each reports its own truth and the coordinator composes them.

ConnectableSource is the third protocol, added when Spotify arrived: per-service authorisation, distinct from AuthProvider, which owns the OmniMusik account itself. Local files implement neither — they need no account.

The test of the split was adding Spotify. It touched no existing source and no existing provider: two new types conforming to two existing protocols, plus a one-case addition to the TrackSource enum on all three codebases.

3 · iOS architecture

Layers, and the one rule about what each may import.

The asymmetry worth knowing

Local tracks come from SwiftData's @Query and stay live as imports happen. Remote sources are fetched into LibraryStore on demand. The unified library is therefore a merge of one reactive source and N fetched ones. Routing local tracks through the same manual refresh would trade real reactivity for a uniformity that helps only the code. The asymmetry is the honest shape of the problem.

Pure decisions, pulled out of the plumbing

Three rules live as pure functions in Domain/ because the code around them cannot be exercised in a test: PlaylistSync.decide (what one playlist needs, given three inputs), SyncEpochRule.decide (whether recorded versions can be trusted at all), and QueueAdvance.nextPlayableIndex (where the queue goes when a track cannot start). Each is a handful of lines, each has a failure mode that would be silent, and each is covered by a small table of cases.

4 · Playing a track

The request path on the phone. The coordinator is the only object that knows more than one provider exists.

Inside the local provider

  • Seeking is stop-and-reschedule with a generation counter. scheduleSegment's completion also fires on cancellation; without the counter every seek reads as end-of-track.
  • Positions are trim-relative. A track trimmed to start at 0:30 reports 0:00 at its first audible sample. The UI never sees the file's absolute timeline.
  • Parametric vs structural edits. Speed, pitch, reverb and EQ mutate live nodes. Trim changes what is scheduled and reschedules — only when the bounds actually move.
  • The audio session is reactivated on every play(). Interruptions deactivate it and iOS does not hand it back; resuming against a dead session is silence with no error.

5 · The Spotify boundary

What happens when the queue crosses from a local file into Spotify — the one transition the platform makes hard.

While a local file plays, Spotify produces no audio, so iOS suspends it. A suspended app cannot accept an SPTAppRemote connection; the only way to wake it is to launch it, which iOS permits only from the foreground. There is no entitlement that keeps a third-party app alive, and the one state that would — Spotify actively playing — is exactly what cannot be true while something else is.

Three fixes were attempted before this was measured, and none could have worked. The logger that settled it cost twenty minutes. The design that shipped is product rather than engineering: make the switch look intentional when it must happen, and from the lock screen keep the music going and report what was skipped.

6 · Data model

What the server stores, and why a playlist is one JSON document rather than a table of rows.

One entry

{
  "id":       "3f1c…",              // the entry's own identity — duplicates are allowed
  "source":   "spotify",            // TrackSource raw value: local | appleMusic | spotify
  "sourceID": "4uLU6hMCjMI75M1A2tKUQC",
  "title":    "…", "artist": "…", "duration": 214.0   // snapshot
}

A playlist must hold an MP3, an Apple Music track and a Spotify track in one ordered list, and those live in different worlds: local tracks are SwiftData rows; streaming tracks are never persisted, because caching someone else's catalogue serves stale copies of their data. So an entry is the (source, sourceID) pair that identifies a track anywhere, plus a snapshot of what to display.

  • Not a relationship — it could only point at local tracks, and relationships are unordered while order is the point.
  • Not Track values — a streaming track is only meaningful while that service answers.
  • The snapshot is the part to defend. Without it a playlist of streaming tracks becomes blank rows the moment the subscription lapses. A playlist should describe itself without a server's permission.
  • The accepted cost: entries are opaque to SQL. "Which playlists contain this track" needs a scan or a secondary index.

7 · Sync

Three mechanisms, each answering a different failure. Read them in order: when, what, and whether the numbers mean anything.

When: the scheduler holds no queue

What: the decision table

Versions, not timestamps: two devices' clocks disagree, and an edit made offline can carry a later timestamp than the server state it is behind. A refused write returns 409 with the server's current copy in the body, so the client can show what differs instead of retrying blindly — which would be last-write-wins wearing a seatbelt. Conflicts are never auto-resolved.

Whether the numbers mean anything: the epoch

Found in production: the local backend ran on in-memory H2, so a rebuild emptied the database and the phone read the absence as N deletions. Unverifiable is treated as replaced, because the two mistakes are not the same size — re-uploading a playlist the server has costs a request and a resolvable conflict; deleting one it does not have costs the playlist.

8 · Authentication

One flow, two clients, no SDK. The API validates tokens; it never sees a password.

  • No AWS SDK on the phone. Amplify is a large dependency for two HTTP calls, and the web client runs the identical flow against the same pool — one mental model.
  • Signing in is optional. Local library, effects and playback need no account; an account buys sync and the web client.
  • The API provisions accounts on first sight of a subject claim. Identity is the sub, never the email — emails change and Sign in with Apple may withhold one.
  • Another user's playlist is 404, not 403. A 403 confirms the id exists and turns the endpoint into an oracle.
  • React StrictMode double-invokes effects and would consume the single-use code twice; the callback memoises the exchange at module level.

What Terraform builds, what ECS builds, and where the one script fits.

Why this and not App Runner

App Runner was the original choice and the reasoning still holds: a managed runtime that takes an image and a port, over hand-wiring the pieces above. AWS closed it to new services on 2026-04-30 and this account cannot create one. Express Mode is the same bargain on ECS; the move cost an afternoon and the network change — App Runner brought its own public endpoint, so the VPC had no public subnets or internet gateway before.

10 · Delivery pipeline

From a commit to a running container, with no stored AWS key anywhere.

  • Jib, not a Dockerfile. No daemon needed on the runner or on a laptop, and dependencies, resources and classes land in separate layers so a source-only change re-pushes kilobytes.
  • The deploy role can deploy and cannot change infrastructure. A leaked static key is the usual way a personal AWS account gets drained; there is none to leak.
  • Schema changes are files. Production runs ddl-auto=validate; Flyway applies V<n>__*.sql before the app starts and validate confirms the entities agree.
