OmniMusik Interview Notes

An iOS app that unifies Apple Music and locally owned audio into one library, queue, and search, with a real‑time effects chain for local files. This document is for studying before an interview — the arguments, the tradeoffs, and an honest account of what is finished.

The pitch

Two lengths. Learn the short one verbatim; let the long one breathe.

Thirty seconds

OmniMusik is an iOS music client that puts streaming and owned audio into a single library, queue, and search. The interesting part is that those two things are not variations on one playback system — they are two incompatible ones. Apple Music plays through a system‑owned player with no sample access; local files run through an AVAudioEngine graph I control frame by frame. The whole architecture is about hiding that split from the UI without pretending it does not exist.

Ninety seconds

I wanted a project where the hard problem was architectural rather than visual. Unifying two playback systems is that, because the incompatibility is structural — Apple Music audio is DRM‑protected, so effects on it are not unimplemented, they are impossible.

So there are two protocols, deliberately kept apart. PlaybackProvider answers “how is this track played.” MusicSource answers “where do tracks come from.” They do not map one‑to‑one, and collapsing them into one interface is the mistake the design exists to avoid.

The local path is where the real audio work lives: a four‑node effects graph with non‑destructive edits that persist per track, seeking implemented as stop‑and‑reschedule, and positions reported relative to the trimmed region so the UI never sees the file’s absolute timeline.

If they push on this

The follow‑up is usually “could you not just tap the output?” No. The protected audio never enters a process‑visible buffer; the system mixes it. Attempting to capture it is a DRM circumvention, not an engineering problem. Saying so plainly is a better answer than speculating about workarounds.

Architecture

Two protocols, one coordinator, and a domain layer with no framework imports.

The two protocols, and why they stay apart

PlaybackProvider — how a track is played. LocalPlaybackProvider wraps AVAudioEngine. An Apple Music provider will wrap ApplicationMusicPlayer.

MusicSource — where tracks come from. LocalMusicSource reads SwiftData; AppleMusicSource will query the catalog and the user’s library.

They are separate because they do not line up. A source can be browsable while playback is unavailable — a lapsed subscription still lets you see the catalog. A provider can play tracks a source no longer lists. Merging them would force every one of those states into a single interface that lies about at least one of them.

The asymmetry worth defending

Local tracks come from SwiftData’s @Query, which keeps the list live as imports and deletions happen. Remote sources are fetched into LibraryStore on demand. So the unified library is a merge of one reactive source and N fetched ones.

That looks like an inconsistency and interviewers will probe it. The answer: routing local tracks through the same manual refresh would trade real reactivity for a uniformity that helps only the code, not the person using the app. The asymmetry is the honest shape of the problem.

The audio engine

Five problems in LocalPlaybackProvider. This is the densest technical material in the project — know it cold.

How is seeking implemented, and what broke?

AVAudioPlayerNode cannot seek. Seeking is stop and reschedule: stop the node, schedule a new segment from the target frame, resume if it was playing.

The trap is that scheduleSegment’s completion handler also fires when playback is cancelled, not only at natural end. So stop() during a seek fires the completion, the coordinator reads it as end‑of‑track, and playback skips to the next song mid‑scrub.

The fix is a generation counter. An integer increments before every stop or reschedule; each completion closure captures the generation that was current when it was scheduled and returns early unless it still matches. Stale callbacks become no‑ops.

Why are positions trim-relative?

A track trimmed to start at 0:30 reports 0:00 at its first audible sample. duration is the audible length, so the scrubber’s range is always 0...duration.

The alternative — exposing absolute file time and asking every view to subtract the trim offset — puts the same correction in the scrubber, the mini player, the lock screen, and the Now Playing view, where it will eventually be wrong in one of them. Converting once at the boundary means the UI never learns the file has an absolute timeline.

Position under a changed playback rate — what does it actually count?

playerTime.sampleTime counts source frames rendered, so at rate = 2.0 it advances at twice wall‑clock speed. That is exactly right for a scrubber, which shows position within the file, and it stays correct across rate changes with no special casing.

If wall‑clock time remaining were ever displayed, it would be (duration − currentTime) / rate. Knowing which of the two a number represents is the whole point.

Why are effects split into two kinds?

Parametric — speed, pitch, reverb, EQ — mutate live nodes and take effect on the next render cycle. That is what makes dragging a slider feel immediate.

Structural — trim — changes what is scheduled, so it requires tearing down and rebuilding the schedule. Rescheduling on every slider tick would stutter, so a trim change reschedules only when the bounds actually moved, and re‑anchors the old absolute position inside the new bounds so adjusting the end handle does not yank playback back to the start.

This is the cleanest example in the codebase of a distinction that is invisible in the UI but drives the implementation.

Why reactivate the audio session on every play, not just on load?

An interruption — a phone call, Siri — deactivates the session on its way out, and iOS does not hand it back automatically. Resuming afterwards would start the engine against a dead session and produce silence with no error thrown, which is the worst kind of bug: no crash, no log, just nothing.

So activateSession() runs on every play(). It is cheap, and it removes an entire class of silent failure.

Lock screen: publish on transitions, never on a timer

MPNowPlayingInfoCenter is not polled. You publish an elapsed time and a playback rate, and the system extrapolates position from there. So it is updated on state transitions — play, pause, seek, track change — and never on the position timer. Republishing several times a second is pure overhead and can make the lock screen scrubber stutter.

The consequence people miss: the Studio’s speed setting must feed the published rate. If it does not, the lock screen extrapolates at 1.0× while the audio plays at 1.5×, and the two drift apart visibly within a minute.

Concurrency

The search fan-out is the best structured-concurrency answer in the project.

One query goes to every source at once via withTaskGroup. Three properties have to hold, none of which come for free:

Failure isolation

Apple Music being down, unauthorized, or slow must not cost you your local results. Each source’s outcome is captured independently and a thrown error becomes a per‑source note in the results, never a failed search. A partial result is still a useful result, so it is surfaced as a footnote rather than an error dialog.

Cancellation, and the race it prevents

Each new query cancels the one in flight. Critically, the cancellation check happens after results are gathered as well as before — otherwise a slow earlier query can finish last and overwrite the results of a faster later one. Typing a word and seeing results for its first three letters is exactly this bug.

Debouncing

A 250 ms sleep inside the task before dispatch, so a network source is not hit on every keystroke. Because it is inside the cancellable task, an abandoned query never reaches the network at all.

Why results are grouped by source, never interleaved

There is no common relevance scale between a filename substring match and Apple’s catalog ranking. Interleaving them would require inventing a comparison that does not exist and presenting it as if it meant something. Grouping is the honest presentation.

Sections are ordered by the canonical TrackSource order rather than by whichever source answered first, so results do not reshuffle between searches.

Cross-source playlists

The payoff of the whole architecture, and the best design question in the project to be asked about.

A playlist has to hold a local file and an Apple Music track in one ordered list. Those two things live in completely different worlds: local tracks are SwiftData rows; Apple Music tracks are not persisted at all, because caching a catalog that changes underneath you means serving stale copies of someone else’s data.

So a playlist can hold neither Track values nor SwiftData relationships. It holds PlaylistEntry: the (source, sourceID) pair that identifies a track anywhere, plus a denormalized snapshot of title, artist, and duration.

Why not a SwiftData relationship?

Two independent reasons. A relationship would have to point at LocalTrackEntity, which would quietly restrict playlists to local files — the exact thing the feature exists to avoid. And relationships are unordered, while order is the entire point of a playlist; preserving it would mean an explicit position column and re-numbering every sibling on each move.

Why denormalize the title and artist?

So the playlist can describe itself when its source cannot answer. Without the snapshot, a playlist of Apple Music tracks becomes blank rows the moment the subscription lapses, the account is unauthorized, or the network is gone — the entries are still there, but nothing can say what they were.

With it, the row still reads correctly and is simply marked unplayable, and the screen distinguishes “Missing” (a deleted local file) from “Not connected” (a source that is unavailable), because the person can only act on one of those.

What is the cost of that choice?

Entries are encoded JSON, so they are opaque to the query engine. A future “which playlists contain this track” screen would need a scan or a secondary index. Volunteering this is better than being caught by it: it is a real tradeoff accepted for ordering and cross-source support, not an oversight.

Are duplicates allowed?

Yes, deliberately — a set that opens and closes on the same record is a real thing people build. Each entry carries its own identity separate from its sourceID, which is what makes removing exactly one of two copies well defined. The “add unless already present” policy lives at the call site rather than buried in the model.

How does resolution work?

MusicSource gained track(forSourceID:) with a protocol-extension default returning nil, meaning “this source cannot supply that track right now”. That is an ordinary answer rather than a throw, so a stubbed Apple Music degrades to unplayable instead of failing the playlist.

Resolution fans out per source, not per entry — a playlist with forty local tracks is one batched lookup, not forty. A queue built from a playlist skips unplayable entries rather than stalling partway through.

Export, while you are in this territory

Edits are non-destructive, which means a slowed-and-reverbed version only exists inside the app. Export bakes one into a file using AVAudioEngine’s manual rendering mode — not AVAssetExportSession, which can trim and transcode but cannot apply a time-pitch or reverb node.

Two failure modes there are silent rather than loud, which is why both are tested: output length must be sourceFrames / rate or every slowed export is truncated and still plays, just stops early; and a reverb tail must be appended or the file ends on a cut that was never audible. The renderer’s graph is a deliberate copy of the player’s — if they drifted, exports would stop sounding like what was auditioned.

Two war stories

For “tell me about a difficult bug.” Both are real, and both have a clean diagnostic arc.

1. Playback died the instant the phone locked

Symptom. Audio stopped the moment the screen locked. But the lock screen itself populated correctly — artwork, title, working transport controls. That combination is what made it hard: it proved NowPlayingCenter was working, which pointed away from the real cause.

What looked right. INFOPLIST_KEY_UIBackgroundModes = audio was present in both the Debug and Release configs of the app target, and it resolved correctly in xcodebuild -showBuildSettings. Everything on the input side checked out.

Root cause. The built Info.plist did not contain the key at all. Xcode’s generated‑plist mechanism honours only a fixed whitelist of INFOPLIST_KEY_* settings, and UIBackgroundModes is not on it. The setting was inert: correct in the project file, resolving in build settings, and silently dropped on the way into the bundle. The app shipped with no audio background mode, so iOS suspended it on lock — exactly the observed behaviour.

Fix. Supply the key from an explicit partial Info.plist, placed outside the synchronized folder so Xcode does not treat it as a bundle resource, with GENERATE_INFOPLIST_FILE left on so every other generated key still merges in on top.

The transferable lesson

The earlier debugging kept verifying the input and finding it correct. The bug only became visible by checking the output — the artifact that actually ships. When a toolchain silently discards valid‑looking configuration, no amount of re‑reading the source will show it.

2. Seeking skipped to the next track

Covered in detail above. The short version for a verbal answer: a completion handler that fires on cancellation as well as completion, mistaken for an end‑of‑track signal, fixed with a generation counter that invalidates in‑flight callbacks. It is a good story because the API’s contract is genuinely surprising and the fix is three lines and a clear invariant.

Decisions to defend

Each of these was chosen against a real alternative. Knowing what was rejected, and why, is what separates a decision from a default.

Why native Swift rather than React Native?

Apple Music has no playback SDK on Android, so cross‑platform was never going to deliver real Apple Music playback there. React Native would also have meant bridging AVFoundation through native modules for the entire effects chain — the most interesting part of the project — so the “shared codebase” benefit evaporates precisely where the work is.

Why is imported audio copied rather than referenced?

Security‑scoped URLs from the document picker do not survive the callback. Storing the URL and reading it later fails once the scope lapses, so files are copied into app‑owned storage at import.

Why no AWS SDK for authentication?

Sign‑in is a plain OAuth2 authorization‑code flow with PKCE against the Cognito Hosted UI via ASWebAuthenticationSession. Amplify Swift is a large dependency for what amounts to two HTTP calls; the hosted UI renders the Sign in with Apple button itself; and the web client will run the identical flow against the same user pool, so there is one mental model rather than two SDKs to reconcile.

PKCE is not optional here. A native binary cannot keep a client secret, so the app client is public and PKCE is what stops an intercepted authorization code from being redeemable.

Why Cognito rather than going straight to Sign in with Apple?

Sign in with Apple stays the intended primary button. Cognito sits underneath it so the clients are decoupled from Apple service availability: email and password work today, Sign in with Apple federates in once configured, and neither client changes when it does.

Why is signing in optional?

The local library, the effects chain, and playback all work with no account. An owned MP3 does not need a server’s permission to play. An account buys cross‑device playlists and the web client; nothing else is withheld. Gating owned files behind a login would be a worse product and a worse answer.

Features deliberately rejected

Stems / source separation — a machine‑learning project wearing a tab. BPM and key detection — would require real analysis, and showing invented values is worse than showing nothing. Uploading local audio to a server — turns a music tool into a file‑hosting service with the storage bill and licensing questions that implies. Spotify — deferred, not rejected: its SDK needs a custom dev client and its own OAuth flow to prove the same architectural point the protocols already prove.

Honest limitations

Prepared answers for “what would you do differently.” Volunteering these reads as judgment; being caught out by them does not.

Test coverage is real but narrow

40 tests pass: 33 unit tests over the playlist rules, AudioEdit identity, Codable round trips, and the renderer’s timeline arithmetic, plus 7 UI tests driving each subsystem end to end.

What is not covered: the generation counter and the trim arithmetic inside LocalPlaybackProvider, which need an engine to exercise and are the two places a bug would be both likely and invisible. Nor is anything about how the audio actually sounds — the export tests assert duration, not fidelity. Describe this as “the domain logic is tested and the subsystems are smoke-tested”, which is true, rather than “it has tests”, which invites the wrong follow-up.

Effects will never work on Apple Music

Worth stating before being asked. It is a structural property of DRM‑protected playback, not a roadmap item, and the domain model encodes it rather than leaving it as a comment.

Simulator is not device

The smoke suite runs on an iOS 18 simulator. Audio routing, interruption handling, and background behaviour all differ on real hardware, and the background‑audio fix in particular can only be confirmed on a device with a physical lock button. Be precise about which parts have run on device and which have only run in the simulator — the status ledger is the source of truth.

Single-device by design, so far

Everything persists locally through SwiftData. Nothing syncs until the backend exists, so “how do you handle conflicts” is currently a design answer rather than an implemented one. Say so.

Phrasing that holds up

“The local playback path and the effects chain are working on device. The search and unified‑library layer compiles and is architecturally complete but I have not finished runtime‑verifying it. Apple Music is blocked on account provisioning, so that source is a stub.”

That sentence is more impressive than a claim of completeness, because it demonstrates you track the difference.

Rapid fire

Short answers to the questions that come up in the last five minutes.

Why @Observable rather than ObservableObject?

Finer‑grained invalidation — views depend on the properties they actually read rather than on every published change — and less ceremony. It is the current recommendation and the deployment target allows it.

Why is everything @MainActor in the playback layer?

Providers drive observable UI state. The cost of hopping actors for transport controls is irrelevant next to having exactly one place where playback state can be mutated. The audio rendering itself is not on the main thread — that happens on the engine’s own render threads.

How are edits stored without touching the audio?

AudioEdit is a value type persisted per track and applied at render time. The source file is never modified, so every edit is reversible and export renders a new file rather than mutating the original.

Where does the queue live?

PlaybackCoordinator, which also carries the per‑track edits for the queue and routes each track to a provider by its source. Providers stay ignorant of what plays next.

What happens at a track boundary between two sources?

The coordinator stops the outgoing provider and loads the incoming one. It is the reason onTrackFinished must not fire for coordinator‑initiated stops — otherwise advancing the queue races with the handoff already in flight.

Why does the domain layer import nothing?

So it stays portable and testable, and so the eventual web client can share the model conceptually even though it shares no code. It is also what keeps framework assumptions from leaking into the types every layer touches.

Anything surprising about testing SwiftUI?

accessibilityIdentifier propagates to every descendant, and an identifier on an enclosing container silently overwrites a more specific one on a child. A mini‑player test failed against a button that was on screen and working, because the container’s identifier had replaced the button’s. The element hierarchy captured in the .xcresult bundle is what showed it — worth knowing that XCTest records that automatically on failure.

Why App Runner rather than ECS Fargate?

A deliberate call against a fixed deadline. Fargate means hand‑wiring a VPC, load balancer, target groups, and task definitions — days that do not buy proportional signal on a portfolio project. The infrastructure is still defined in Terraform with a container pipeline. Being able to say when you would move to Fargate is the part that matters.
